# AI任务结果错乱排查与修复

## 问题描述
提交14个任务，前7个用图A，后7个用图B。结果：第1个正确（图A），第2-14个全是图B的结果。

## 根因分析

### 后端流程回顾
1. **SubmitTask** — 每个任务独立存储：`storage/ai/input/{taskNo}/original.png`，DB记录各自的 `InputImagePath`
2. **FetchPendingTask** — 按 `Create_time` 升序取第一个 `pending` 任务，原子更新为 `processing`，返回 `InputImageUrl`
3. **CallbackSuccess** — N8N 根据 `taskNo` 回调，下载结果图到 `storage/ai/output/{taskNo}/result.png`

### 后端代码无bug
- 每个任务的 `InputImagePath` 是独立的（包含各自的 taskNo）
- `FetchPendingTask` 原子操作正确，不会并发取到同一任务
- `CallbackSuccess` 按 taskNo 更新，不会更新错任务

### 问题在N8N工作流侧
N8N 拉取任务后，没有正确使用返回的 `inputImageUrl`。最可能的原因：
1. **N8N 节点缓存了变量** — 某个节点把 inputImageUrl 存到了全局变量，后续任务复用了旧值
2. **N8N 并发处理** — 多个任务并发处理时共享了同一个输入图引用
3. **N8N HTTP节点配置** — 没有正确从 fetch 响应中提取 `inputImageUrl`

## 修复方案

### 1. 后端增强日志（排查用）
在 `FetchPendingTask` 和回调处增加详细日志，记录每次 fetch 返回的 taskNo 和 inputImageUrl，方便对照 N8N 日志排查。

**文件**: `ZR.ServiceCore/Services/AiTaskService.cs`
- `FetchPendingTask`: 记录返回的 `taskNo` 和 `inputImageUrl`
- `CallbackSuccess`: 记录收到的 `taskNo` 和 `outputImageUrl`

### 2. Fetch 接口返回 inputImageUrl 的同时，增加输入图的文件哈希校验（可选）
在任务表新增 `InputImageHash` 字段，提交时计算图片 MD5 存入。N8N 回调时可对比，防止图片混淆。（这个改动较大，暂不实施，仅记录）

### 3. N8N 工作流修复建议（需要用户操作）
检查 N8N 工作流中：
- fetch 节点之后，确认 `inputImageUrl` 是否正确传递到后续节点
- 是否有 Set 节点把 URL 写入了全局变量
- 处理节点是否使用的是当前 fetch 返回的 URL，而非缓存值

## 涉及文件

| 文件 | 改动 |
|------|------|
| `ZR.ServiceCore/Services/AiTaskService.cs` | 增强 FetchPendingTask 和 CallbackSuccess 的日志 |

## 验证方式
1. 重启后端查看日志
2. 提交2个不同图片的任务
3. 检查日志中每次 fetch 返回的 taskNo 和 inputImageUrl 是否不同
4. 检查 N8N 侧日志，确认它收到的 inputImageUrl 是否正确
